# **postlink 0.1.2.9000** (development version)

### Breaking Changes (Bayesian mixture fits, aligned with `adjMixture()`)
* `estimates$m.coefficients` of `glmMixBayes` and `survMixBayes` fits now holds the posterior draws of the mismatch-indicator model of `m.formula`, on the scale and with the sign of the `m.coefficients` of `glmMixture()` and `coxphMixture()`: a record not flagged as a safe match is a mismatch with probability `plogis(Z %*% m.coefficients)`. With linkage covariates it equals `-gamma`; with `m.formula = ~1` it is the single column `"(Intercept)"`, equal to `qlogis(1 - theta)`.
* The outcome-model parameters of the mismatch component (component 2) moved from `estimates$m.coefficients` to `estimates$coefficients2`, and `m.dispersion`, `m.shape` and `m.scale` were renamed `dispersion2`, `shape2` and `scale2`. The same names are used by `summary.glmMixBayes()` (elements `coefficients2`, `dispersion2` and the new `m.coefficients`), `confint()` and `vcov()` (`block = "coefficients2"`, `"dispersion2"`, ...; `block = "m.coefficients"` now selects the mismatch-indicator model) and `posterior_draws()` / `coda::as.mcmc()` (columns `coefficients2[...]`, `m.coefficients[...]`, `dispersion2`, `shape2`, `scale2`). The methods convert fits saved with postlink 0.1.2 on the fly, and `print()` shows `summary.glmMixBayes` objects saved with the old names with their component-2 tables under component 2 (other methods need the summary to be recomputed). `summary.survMixBayes()` keeps its element names (`coef1`, `coef2`, `shape1`, ...).
* The engine argument `safe` of `glmMixBayes()` and `survregMixBayes()` is now `safe.matches`, the name used by `adjMixBayes()`, `adjMixture()`, `glmMixture()` and `coxphMixture()` (it keeps its position, so `safe =` still works by partial matching).
* Posterior tables use the column names of `glmMixture()` and `stats::confint()`: `"Estimate"` (posterior mean), `"Std. Error"` (posterior standard deviation), `"2.5 %"` and `"97.5 %"` (posterior quantiles); the first column of the coefficient tables of `summary.glmMixBayes()` was `"Estimates"`, and its dispersion tables now include the interval columns. The tables of `summary.survMixBayes()` now have one row per parameter and these columns (previously one column per parameter and one row per quantile); its `probs` argument (default now `c(0.025, 0.975)`) adds further quantile columns, e.g. `"50 %"` for the median. `confint()` labels the interval bounds `"2.5 %"` / `"97.5 %"` (formatted as by `stats::confint()` at every level, e.g. `"0.05 %"` / `"99.95 %"` for `level = 0.999`), as do `predict()` and the printed results of `mi_with()` (previously `"Std.Error"`, `"CI.lwr"`, `"CI.upr"`). This includes the named bounds of the scalar parameters in the list returned by `confint.survMixBayes()`: `confint(fit)$theta` is named `"2.5 %"`, `"97.5 %"` (previously `"2.5%"`, `"97.5%"`).
* `fitted()`, `residuals()`, `df.residual()` and `deviance()` stop with an informative message for `glmMixBayes` and `survMixBayes` fits instead of silently returning `NULL`.
* Linkage covariates are centred: with covariates in `m.formula` (or a `Z` with more than one column in `glmMixBayes()` / `survregMixBayes()`), the sampler centres the non-intercept linkage covariates at their mean over the records not flagged as safe matches (over all records when every record is safe). The `gamma_intercept` prior, whether derived from `m.rate` / `m.rate.sd`, from a `theta` prior, the default or given by the user, therefore refers to a record with average linkage covariates, the point at which `adjMixture()` applies `m.rate`, instead of to linkage covariates equal to zero (with an uncentred score such as a match weight, `m.rate` described records with a score of zero). The likelihood and the `gamma_slope` prior are unchanged, but posteriors change because the intercept prior moves. `estimates$gamma` and `estimates$m.coefficients` are still reported for the original covariates, starting values `control$init$gamma` are given for the original covariates, and the centre is stored in the new element `z_center`. Whether the prior on the match probability identifies the components (see the label-switching rules under *Bayesian Mixture Engine*) is decided on this centred intercept prior, and the warning on atypical safe matches compares component 1 with the prior mean of the match probability at that average record. `print.adjMixBayes()` reports the prior on `theta` implied by `m.rate` for a record with average linkage covariates and shows their mean over the records of `linked.data` not flagged as safe matches (over all records when every record is a safe match; `z_center` averages over the analysed records and can differ slightly). `summary()` of fits with linkage covariates prints the `gamma_intercept` prior and `z_center` under the `gamma` table (summary elements `gamma_intercept_prior` and `z_center`).
* Weibull fits report the identified intercept: for `dist = "weibull"` with an intercept column in the design matrix (a column of ones, whatever its name), `estimates$coefficients` and `estimates$coefficients2` now hold `(Intercept) + log(scale)` and `(Intercept) + log(scale2)`, comparable to the `(Intercept)` of `survival::survreg()`, and `coef()`, `print()`, `summary()`, `confint()`, `vcov()`, `posterior_draws()`, `coda::as.mcmc()` and the effective-sample-size check use them. Only these sums are identified by the data; the posteriors of the sampled intercept and of `scale` depended on their priors. `estimates$scale` and `scale2` are kept (their posteriors reflect their priors when the design has an intercept column), the prior-data conflict warning still refers to the sampled intercept (on which its prior is placed), and `predict()` gives the same linear predictors as before (it adds `log(scale)` only when the intercept does not already include it). The new element `intercept_includes_logscale` records this; designs without an intercept column are reported as sampled. Weibull fits saved with earlier versions lack this element and are still reported with the sampled intercept (their predictions include `log(scale)`); refit them to obtain the identified intercept. Starting values `control$init$beta1` / `beta2` still refer to the sampled intercept. `summary.survMixBayes()` gains `inv_shape1`, the posterior of `1 / shape`, which is comparable to the `Scale` of `survreg()`, and labels the scale blocks as scale multipliers of `exp(X beta)`.

### New Features (Bayesian mixture fits)
* Fitted objects gain `match.prob`, the posterior probability that each record is a correct match (the share of the stored draws allocating it to component 1; 1 for safe matches), named after the analysed records, as in `glmMixture()` fits. `summary()` reports the average posterior correct-match probability over all records (safe matches counted as 1, the average printed by `adjMixture()` fits) and over the records not flagged as safe matches (which `theta` describes), with the number of records of each.
* `summary()` shows the mismatch-indicator model (`m.coefficients`, "Mismatch Model Coefficients (logit of the mismatch probability)") next to the `theta` / `gamma` tables; `print()` shows the posterior means of the correct-match coefficients, of `theta` (or of the mismatch-model coefficients), of the component-1 dispersion or shape, and the numbers of records and safe matches (`print.survMixBayes()` now uses significant digits, so small coefficients no longer print as 0). The `theta`, mismatch-model and `gamma` tables of `summary.glmMixBayes()` and `summary.survMixBayes()` carry the same headings, with the same note on the records not flagged as safe matches.
* `predict.glmMixBayes()` gains `newdata`, its second argument as in `predict.glmMixture()`: a data frame is turned into a model matrix with the stored terms of a `plglm()` fit, and a numeric matrix is taken as the model matrix, so positional calls of postlink 0.1.2 such as `predict(fit, X, "response")` keep working. `newx` still takes a model matrix, but it is now the last argument (after `na.action`), so give it by name; the abbreviation `new =`, which matched `newx` in 0.1.2, now matches both `newdata` and `newx` and raises an error, so write `newx =` (or `newdata =`) in full. Predictions are named after the rows of the model matrix (the row names of `newdata`, or the analysed records), as by `predict.glm()`, also by `predict.survMixBayes()`; rows of `newdata` with missing covariates give `NA` predictions. Without new data, predictions are made for the analysed records, also when the fit stores only its model frame; records dropped at fit time because their linkage covariates are missing are left out (the design matrix stored by `plglm(..., x = TRUE)` includes them). Misspelled or unused arguments raise an error instead of being ignored (e.g. `newdata` given to a fit without stored terms returned the in-sample predictions).
* `predict.survMixBayes()` likewise accepts a data frame in `newdata` (with a new `na.action` argument) for fits from `plsurvreg()`, besides a model matrix, and without new data predicts the analysed records from the stored design matrix or model frame.
* `vcov()` gains a `block` argument with the blocks of `confint()` (for `survMixBayes` fits also the list names `"coef1"`, `"coef2"`, `"shape1"`, `"scale1"`); `confint.glmMixBayes()` and `vcov()` refuse unused arguments. `confint.survMixBayes()` keeps returning the named list (now with an `m.coefficients` element), returns a matrix for `block = "<name>"` and for coefficient names or indices of component 1 in `parm`, as `confint.glmMixBayes()` does. In `parm`, both methods accept every block name that `block` accepts (e.g. `parm = "coefficients"`; for `survMixBayes` fits this selects the list element `coef1`).
* `mi_with()` for `glmMixBayes` fits stores and prints the refitted model (`refit`, `family`, `link`, `call`); Gaussian models with a non-identity link are refitted with `glm()` (they were refitted with `lm()`, ignoring the link), and `family` may also be a family function or its name; the name `"gamma"` (in any case) gives `Gamma(link = "log")`, as in `glmMixture()` (`base::gamma()` is not a family).
* New help sections *Correspondence with adjMixture()* in `?glmMixBayes` and `?survregMixBayes` list the corresponding outputs and arguments of the two mixture frameworks and their differences (e.g. `m.rate` is an upper bound in `adjMixture()` and the centre of a prior in `adjMixBayes()`; the EM uses the marginal density of the outcome for mismatches). `?posterior_draws` documents the column names; `?survregMixBayes` states that the Weibull `scale` multiplies `exp(X beta)` and is not the `Scale` of `survreg()` (which is `1 / shape`), and `?mi_with.survMixBayes` that the pooled estimates are Cox log hazard ratios (about `-shape * beta` for the Weibull distribution).

### Bayesian Mixture Engine
* Replaced the Stan (NUTS) backend of `glmMixBayes()` and `survregMixBayes()` with a purpose-built Gibbs sampler written in C++ (Rcpp / RcppArmadillo): match indicators are drawn exactly, regression blocks use Laplace-approximation independence Metropolis-Hastings proposals, Gaussian coefficients and the match probability use conjugate / collapsed updates, and dispersion, shape and scale parameters use slice sampling. The package no longer depends on `rstan`, `StanHeaders`, `rstantools`, `RcppParallel`, `RcppEigen`, `BH` or `label.switching`; it compiles in well under a minute and typical fits take seconds instead of minutes, with posteriors that agree with the Stan implementation for the same priors (see *Bug Fixes* for prior strings that 0.1.2 read differently).
* Prior strings keep the Stan-style syntax but are now validated against a fixed menu: `normal(mu, sd)` for coefficients; `normal`, `cauchy`, `student_t` (truncated at zero), `gamma`, `exponential`, `lognormal` and `inv_gamma` for dispersion and shape parameters; `gamma`, `exponential` and `lognormal` for the Weibull scale; `beta(a, b)` for `theta`. Unsupported distributions or invalid arguments raise an informative error, unrecognised prior names a warning. The distribution written is now used (in 0.1.2 it was ignored; see *Bug Fixes*). The default priors are unchanged and are now documented in full (section *Prior distributions* of `?glmMixBayes` and `?survregMixBayes`); the priors actually used are stored in the new `priors` element of fitted objects, as written (an `exponential(rate)` prior keeps this name and is used as the same distribution, `gamma(1, rate)`), without `intercept1` and `intercept2` when the design matrix has no intercept column (see *Linkage Information in `adjMixBayes()`*).
* Added a multi-start pilot phase and a native ECR-iterative label alignment step so that component 1 consistently denotes correct matches. The native implementation fixes a pivot defect of `label.switching::ecr.iterative.1` that affected records allocated to the mismatch component in every draw, and no longer fails when every draw allocates all records to one component. When the draws are relabelled is described in the next item.
* Label switching is handled by three rules, decided before sampling and stored in `diagnostics$orientation` (section *Label switching* of `?glmMixBayes` and `?survregMixBayes`): (1) `"safe matches"`: safe matches identify the components; (2) `"match-rate prior"`: otherwise a prior on the match probability that is not symmetric under exchanging the labels identifies them (a `theta` prior `beta(a, b)` with `a != b`, e.g. the prior derived from any `m.rate` other than 0.5, or with linkage covariates a `gamma_intercept` or `gamma_slope` prior with a non-zero mean): component 1 is the correct-match component of the more probable labelling; (3) `"majority component"`: otherwise component 1 is the component holding the majority of the records. Under rule 2 a Gibbs chain stays in the labelling it starts in, which the pilot chains can reach more or less at random when both labellings fit the data, so the sampler estimates, over the last sweeps of the selected pilot chain (at the starting state with `pilots = 0`), the log ratio of the posterior probabilities of the labelling with the components exchanged and of the labelling of the chain (`diagnostics$orient_lp_change`), and exchanges the labels of the starting state of the main chain when it is positive (`diagnostics$pre_oriented`; starting values in `control$init` are respected). After sampling, the share of the posterior probability held by the other labelling is estimated from the stored draws (`diagnostics$other_labelling`, also stored under rule 3, where it is 0.5 for identical component priors), and a warning is issued when it exceeds 0.05 (the prior identifies the components only weakly, e.g. for `m.rate` close to 0.5 or a large `m.rate.sd`, so that component 1 may describe the mismatches) and, worded more strongly, when it exceeds 0.5 (the chain stayed in the less probable labelling). Under rule 3 the sampler exchanges the labels of the starting state of the main chain when component 2 holds the majority of the records on average over the last sweeps of the selected pilot chain (`diagnostics$pre_oriented`; with `pilots = 0` the initial allocation decides, which only approximates the labelling the chain reaches; starting values in `control$init` are respected), unless the component-specific priors make the labelling with component 1 as the majority much less probable, since a chain started in a much less probable labelling may not leave it within the run (e.g. `beta2 = "normal(0, 0.5)"` or tighter, i.e. mismatches without slope, when the correct matches are a minority with a slope). Exchanging all labels changes the posterior only through these priors, so the sampler first estimates the log ratio of the posterior probabilities of the two labellings over the last sweeps of the selected pilot chain (at the starting state with `pilots = 0`; `diagnostics$orient_lp_change`; exactly 0 for identical component priors) and exchanges the labels when it is at least -2. Below -2 two check chains of `pilot.iterations` sweeps, started from the selected pilot state with and without the labels exchanged, decide (`diagnostics$orient_check`; not run with `pilots = 0`): the starting state is kept (`diagnostics$orient_refused`) only when, over the second half of its sweeps, the chain with the labels exchanged returns to the original labelling or its average log posterior stays below that of the other chain by more than `max(2, 2 * se)`, `se` being the Monte Carlo standard error of the difference (a few units for slowly mixing chains). The estimate alone does not suffice because it refers to the mirror image of the region visited by the pilot chain, while a chain started there can move on to another mode of the same labelling: for the `"binomial"` defaults it falls below -2 once the squared slopes of the majority exceed those of the minority by more than about 33 (e.g. with many covariates), and the chain with component 1 as the majority then usually finds a mode of comparable posterior probability. The pilot scores are stored in `diagnostics$pilot_lp`. After sampling, the draws are relabelled (ECR alignment followed by a global majority flip; `diagnostics$relabelled`, and `diagnostics$n_swapped` counts the relabelled draws), also when the component-specific priors differ, as for the `"binomial"` defaults (`beta1 = normal(0, 2.5)`, `beta2 = normal(0, 5)`), unless these priors make the labelling with component 1 as the majority much less probable: as for the starting state, the global flip is made only when the log ratio of the posterior probabilities of the exchanged and the aligned labelling, estimated from the aligned draws, is at least -2 (a chain can drift after its start into the labelling that such priors favour). Relabelling renames the components of a draw without changing the fit it describes, so component 1 is the majority component in every reported draw (unless the flip is refused), also when the chain switched between the two labellings, as mixtures of logistic regressions with weakly separated components do. For component priors that differ, the component 1 of a relabelled draw was sampled under the component-2 priors: `diagnostics$lp` is the log posterior of the reported draws (for a relabelled draw, that of the draw with its components renamed), and `priors` holds the priors of the components as sampled. When the exchange of the starting state or of the aligned draws is refused, the component-specific priors identify the components, and component 1 holds the minority of the records. Under rules 1 and 2 the draws are reported as sampled. In 0.1.2 the draws were always relabelled (a global majority flip followed by ECR alignment), which changes results: with an asymmetric `theta` prior such as `beta(3, 7)` the global flip could report the majority component as component 1 against the prior, and the ECR step exchanged individual draws, which cut the posterior of `theta` at 0.5. The new `m.rate` prior and `gamma_slope` priors of non-zero mean identify the components in the same way (rule 2), so their draws are never relabelled either. `diagnostics$ecr_share` stores the share of the stored draws that ECR alignment, applied to the records not flagged as safe matches, exchanges or would exchange. When the draws are reported as sampled and this share exceeds 0.1, a warning reports that the chain visited both labellings of the mixture (a multimodal posterior or weakly separated components); the reported draws then mix both labellings, so posterior means of the component-specific parameters and of `theta` should not be interpreted (`summary()` adds a note saying so). Warnings are also issued when, under rule 3, component 1 holds fewer than half of the records on average because the component-specific priors refused the exchange of the starting state or of the aligned draws (the warning explains the refusal and, for the `"binomial"` default priors, which are not meant to identify the components, recommends `m.rate` or safe matches), and when, under rule 3 with component priors that differ, after the labels of the starting state were exchanged, the average log posterior of the stored draws as sampled lies below that of the selected pilot chain, allowing for the change of level between the check chains (or else the estimated change), by more than 5 or twice the standard deviation of the log posterior of the stored draws, whichever is larger (a chain trapped in a minor mode). The warnings and the `summary()` note of `survMixBayes` fits refer to `?survregMixBayes`.
* `diagnostics` now stores acceptance rates, the number of relabelled draws, the log posterior of every reported draw (see the label-switching rules) and the average log posterior of every pilot chain, the MCMC settings, the label orientation and the number of safe matches; a warning is issued when a Metropolis-Hastings acceptance rate is below 0.2.
* New `control` settings `thin`, `pilots`, `pilot.iterations`, `collapse`, `init` and `verbose`, all validated. The Stan-specific `cores` setting is accepted and ignored (the sampler runs a single chain); `adapt_delta`, `max_treedepth` and any other unknown setting are ignored with a warning. Modelling arguments that the Bayesian models do not support (`weights`, `offset`, `start`, ...), passed to `glmMixBayes()`, `survregMixBayes()`, `plglm()` or `plsurvreg()`, are refused by name, before they are evaluated, instead of being ignored (so that `offset = log(e)` with `e` a column of the linked data gets this error rather than "object 'e' not found"), and so are `offset()` terms in the model formula of `plglm()` / `plsurvreg()` with an `adjMixBayes` adjustment (see *Bug Fixes*); a `data` argument passed to `plglm()` / `plsurvreg()` is ignored with a warning (the data come from the adjustment object).
* Added `posterior_draws()` and `coda::as.mcmc()` methods for `glmMixBayes` and `survMixBayes` objects so that standard MCMC diagnostics (`coda::effectiveSize()`, trace plots, Gelman diagnostics across seeds) can be applied directly. The `as.mcmc()` methods use delayed S3 registration, so `coda` stays optional (Suggests) and is not loaded together with postlink; the package now requires R (>= 3.6.0).
* The sampler is robust to covariates and outcomes on extreme scales: the log survival of right-censored gamma records is computed on the standardised scale (it could be `NaN`, which put such records in the mismatch component), component log-likelihoods that are not finite no longer stop the update of `theta`, starting values are scale-aware (a Gaussian outcome recorded in very small units started from a residual SD of 1 and ended in a minor mode), the Newton search behind the Laplace proposals uses the scale-free Newton decrement as its convergence criterion and an equilibrated Cholesky factorisation, and the derivatives of the censored gamma log survival use an asymptotic expansion in the far tail.
* Every sweep also proposes joint moves of all continuous parameters (coefficients of both components, `theta` or `gamma`, dispersions) with the match indicators integrated out, using random-walk and independence Metropolis-Hastings proposals estimated from the burn-in and fixed while draws are stored (a partially collapsed Gibbs sampler). This breaks the strong dependence between coefficients and indicators when records carry little information: on the paper's logistic example (Model 8) the effective sample size of the intercept rises from about 300 to about 1,000 of 9,000 draws for about 30% more computing time. The acceptance rates are stored in `diagnostics$accept_joint`.
* The slice width of the collapsed `theta` update is fixed while draws are stored (a width following the current `theta` made the update slightly irreversible); the pilot chains and the burn-in still adapt it.
* Label alignment runs in C++ without S x N temporaries, the allocation matrix is allocated before sampling starts, and a warning is issued before sampling when the stored allocations need more than 1 GB (use `thin`). Interrupts (Esc / Ctrl-C) are honoured within a quarter of a second.
* The acceptance rates in `diagnostics$accept` and the low-acceptance warning refer to the reported components after relabelling. The message "Global label swap performed" (and the messages on the orientation of the starting state) is shown only with `verbose = TRUE`; the relabelling is recorded in `diagnostics$relabelled`, `diagnostics$n_swapped`, `diagnostics$pre_oriented`, `diagnostics$orient_refused`, `diagnostics$orient_check` and `diagnostics$orientation`.

### Diagnostics
* The effective sample size of every parameter is stored in `diagnostics$ess`. A warning is issued when it is below 100 for a correct-match coefficient, `theta` or, with linkage covariates, a mismatch-model coefficient (named `m.coefficients[...]`, as in the R-hat check; its effective sample size is that of `gamma`) in runs with at least 1000 iterations after the burn-in, whatever the thinning (thinning a long run lowers the number of stored draws, which the message reports, but not the length of the run; since the effective sample size cannot much exceed the number of stored draws, a thinned run that stores fewer than 200 draws is also advised to reduce `thin`), and `summary()` notes low effective sample sizes in any run.
* The single-chain split R-hat replaces the R-hat that rstan computed for the Stan-based 0.1.2 fits: the rank-normalised split R-hat of Vehtari et al. (2021), the larger of its bulk and folded (tail) versions, computed from the two halves of the stored draws as `rstan::Rhat()` does for one chain (implemented in base R). It is stored in `diagnostics$rhat` for the correct-match coefficients, `theta` (or, with linkage covariates, the mismatch-model coefficients), the component-1 dispersion or shape and `lp` (`NA` for constant draws; `Inf`, where `rstan::Rhat()` gives `NA`, when each half of the chain is constant but the two halves differ, so that this case counts as not converged). A warning is issued when a value exceeds 1.05 in runs with at least 1000 iterations after the burn-in and at least 200 stored draws (with fewer, nearly independent draws exceed 1.05 by chance too often), and `summary()` notes such values in any run. A single-chain R-hat detects drift within the run but not a mode that the chain never visited, so the warning and the help pages recommend comparing fits with several seeds, e.g. with `coda::gelman.diag(coda::mcmc.list(coda::as.mcmc(fit1), coda::as.mcmc(fit2)), multivariate = FALSE)` (the multivariate statistic fails for fits with linkage covariates, whose draws contain both `gamma` and `m.coefficients = -gamma`). The note of `summary()` says that the split R-hat is noisy when fewer than 200 draws were stored (`n_draws` in the summary object).
* The posterior tables of `summary()` for the correct-match coefficients, `theta`, the mismatch model (`m.coefficients`, `gamma`) and the component-1 dispersion (GLMs) or shape and `1 / shape` (survival models) gain the columns `"MCSE"` (Monte Carlo standard error of the posterior mean: the posterior standard deviation divided by the square root of the effective sample size), `"ESS"` and `"Rhat"`, after the columns `"Estimate"`, `"Std. Error"` and the quantiles. The tables of component 2 keep their four columns. For fits saved without `diagnostics$ess` and `diagnostics$rhat`, `summary()` computes them from the draws, for the tables and for its notes. The printed tables show the effective sample size as a whole number and the split R-hat with three decimals (with significant digits, values such as 1.0002 printed as 1).
* The coefficients of the correct-match component are checked against their priors, in one warning per fit. Before sampling, the outcome model is fitted without the mixture (`stats::glm.fit()`, `stats::lm.fit()` for Gaussian outcomes, or `survival::survreg(dist = "weibull")`): to the safe matches when there are at least `p + 5` of them, otherwise (or when the fit to the safe matches fails or warns, or its outcome does not vary) to all records, ignoring the linkage errors. A coefficient with a default prior is flagged when this estimate lies more than 3 prior standard deviations from the prior mean, and the warning says when the posterior standard deviation stayed above 0.9 times the prior standard deviation, i.e. when the prior dominates the estimate (whether or not the posterior mean moved far from the prior mean). This covers a Gaussian outcome in very large units (whose residual standard deviation absorbs the outcome) and covariates in very small units, for which the posterior collapses onto the default prior: the posterior means then stay within a few prior standard deviations of the prior means although the estimates are off by orders of magnitude. This part of the check is reported even when the fit stops because the log posterior is not finite in any stored draw. After sampling, a coefficient with any prior is flagged when its posterior mean lies more than 3 prior standard deviations from its prior mean, and a coefficient with a supplied prior (even one equal to the default) when that prior dominates the estimate although the estimate without the mixture lies more than 3 prior standard deviations from the prior mean and, allowing for its standard error, more than 3 times the square root of the prior variance plus the squared standard error (the message then says that the supplied prior conflicts with the data; a supplied informative prior may still dominate data that carry little information without a warning). For Weibull fits with an intercept column, whose intercept prior applies to the sampled intercept, the message also quotes the posterior mean of the intercept that `summary()` reports (with `log(scale)` added). The message calls a prior "default" only when the corresponding `intercept1` or `beta1` entry was not supplied, explains that the default priors are not rescaled to the data and suit outcomes and covariates of order one, uses the column names of the design matrix (unnamed columns are named as described under *Output Objects*) and refers survival fits to `?survregMixBayes`. The help-page examples of `adjMixBayes()`, `glmMixBayes()` and its methods give priors on the scale of the data (the cubic polynomial of the year of birth has slopes of up to about 60 years), and the example of `glmMixBayes()` names the columns of its design matrix.
* The log posterior of the stored draws is checked after sampling, also when no pilot chains are run (with `control$init` or `pilots = 0`): the fit stops with an error when it is not finite in any stored draw (the draws are then not valid) and warns with the share of the stored draws when it is not finite in some of them. A warning is also issued when no pilot chain reaches a finite log posterior (the main chain then starts from the initial values). The messages point to an outcome or covariates on extreme scales.
* `diagnostics$accept` (the acceptance rates of the Metropolis-Hastings updates) and `diagnostics$accept_joint` (those of the joint moves) refer to the sweeps after the burn-in (`diagnostics$accept` to all sweeps when `burnin.iterations = 0`); the low-acceptance warning is issued only when at least 50 sweeps enter the rates, since rates over fewer sweeps are too imprecise. `diagnostics$joint_burnin` records the burn-in draws collected to estimate the proposal of the joint moves and the number they need, and `summary()` notes when the joint moves were off (`diagnostics$accept_joint` is `NA`) because the burn-in was too short, with the burn-in that would suffice.
* Warnings for designs with linearly dependent columns, for linkage covariates of `m.formula` (or columns of `Z`) that are linearly dependent over the records not flagged as safe matches, which inform the match-probability model (their `gamma` coefficients are then identified by the `gamma_slope` prior only; they were accepted silently), for fits in which every record is a safe match, and for safe matches that anchor a component holding a minority of the other records although the prior does not make correct matches the minority (the safe matches are then possibly atypical of the correct matches).

### Linkage Information in `adjMixBayes()`
* `adjMixBayes()` gains the arguments `m.formula`, `m.rate`, `m.rate.sd` and `safe.matches`, mirroring `adjMixture()`. Known correct matches (`safe.matches`: logical or 0/1, given as a vector, an unquoted column name or a column name in quotes) are fixed in the correct-match component and excluded from the match probability model; `m.formula` replaces the constant match probability `theta` by a logistic regression on linkage covariates, `theta_n = inv_logit(Z_n gamma)`, with decoupled `gamma_intercept` / `gamma_slope` priors (slopes default to `normal(0, 2.5)`, so linkage covariates should be roughly on a unit scale); `m.rate` with `m.rate.sd` (a probability-scale prior SD, default 0.1) is converted to a moment-matched `beta(a, b)` prior on `theta` or, with covariates, to a normal prior on the intercept of `gamma` (for a record with average linkage covariates, see *Breaking Changes*) with the exact logit-scale moments of that beta distribution. An explicit `theta` (or `gamma_intercept`) prior takes precedence over `m.rate`, with a message; whether `(m.rate, m.rate.sd)` defines a beta distribution (`m.rate.sd^2 < m.rate * (1 - m.rate)`) is checked only when `m.rate` is used (each value is still checked on its own), so that e.g. `adjMixBayes(d, m.rate = 0.01, priors = list(theta = "beta(2, 2)"))` no longer fails on the default `m.rate.sd`. A warning is issued when a shape parameter of the implied beta distribution is below 1 (e.g. `m.rate = 0.05` with the default `m.rate.sd = 0.1`): without linkage covariates the density of this prior on `theta` is then unbounded at 0 or 1; with covariates the warning describes the normal prior on the logit scale that is actually used, by the median, 95% interval and standard deviation of the match probability of a record with average linkage covariates (e.g. a standard deviation of 0.27 for `m.rate = 0.05` and the default `m.rate.sd = 0.1`). The warning and the note of `print.adjMixBayes()` state the bound on `m.rate.sd` below which both shape parameters exceed 1 and the density is bounded, rounded down (0.04755 for `m.rate = 0.05`). `?adjMixBayes` explains that a bounded density does not give a mode near `1 - m.rate`, which needs a smaller `m.rate.sd`, and that with covariates the probability-scale mean and standard deviation of the prior are close to `1 - m.rate` and `m.rate.sd` only for a moderate `m.rate.sd`.
* Linkage information passed to `plglm()` or `plsurvreg()` (`m.formula`, `m.rate`, `m.rate.sd`, `safe.matches`) with an `adjMixBayes` adjustment raises an error that points to `adjMixBayes()` (it previously failed with an R argument-matching error or was ignored with a warning).
* Prior strings are validated when the adjustment object is created; records whose linkage covariates are missing are dropped at fit time with a warning (as in `adjMixture()`); `m.formula` must keep its intercept and must not contain `offset()` terms.
* Component-specific prior entries need their component number: `intercept`, `beta`, `sigma`, `phi`, `shape` and `scale` without 1 or 2 are reported as unrecognised when the adjustment object is created (they were accepted there and dropped only at fit time), with a hint to write e.g. `intercept1` and/or `intercept2`, and `print.adjMixBayes()` marks them as ignored; the fit does not repeat this warning for these entries (entries added to the adjustment object after its creation, and priors given to `plglm()` or `plsurvreg()` themselves, are checked when the model is fitted). When the design matrix has no intercept column (e.g. `y ~ 0 + x`), every column receives the `beta1` / `beta2` prior: supplied `intercept1` / `intercept2` priors are now reported as not used, with a warning, and left out of `fit$priors`, which listed them as used. The intercept prior applies only to a first column of ones: a column of ones elsewhere (named `"(Intercept)"` when it has no name, see *Output Objects*) receives the `beta1` / `beta2` prior, and the warning then names it and suggests putting it first. A message reports when, with linkage covariates, an explicit `gamma_intercept` prior overrides a `theta` prior, and when a `gamma_slope` prior overrides its alias `gamma`; `print.adjMixBayes()` says so as well.
* `glmMixBayes()` and `survregMixBayes()` accept the corresponding low-level arguments `Z`, `safe.matches`, `m.rate` and `m.rate.sd` (placed after `control`, so that code passing `control` as the fifth argument keeps working); `plglm()` and `plsurvreg()` align the linkage covariates and safe-match indicators with the rows of the outcome model automatically.
* `summary()` of `glmMixBayes` and `survMixBayes` fits reports the posterior of `theta` (constant match probability) or of the `gamma` coefficients (logistic match probability model), labelled as referring to the records not flagged as safe matches when safe matches are used; `confint()` for `glmMixBayes` gains a `block` argument to select `"coefficients"`, `"coefficients2"`, `"m.coefficients"`, `"theta"`, `"gamma"`, `"dispersion"` or `"dispersion2"` (a single block name in `parm`, e.g. `parm = "theta"`, also selects the block, as for `survMixBayes`), and `confint()` for `survMixBayes` returns a `gamma` block in place of `theta` when covariates are used, accepts `block =` like the GLM method and refuses other unused arguments.
* `print.adjMixBayes()` describes the match probability model, lists all default priors, applies the same prior precedence rules as the fitting functions and shows the prior on `theta` implied by `m.rate`. Without priors it prints "None specified; the defaults below are used." (it said "Using symmetric defaults", although the `"binomial"` slope defaults differ between the components and the prior derived from `m.rate` is not symmetric).

### Input Validation
* `glmMixBayes()` checks the link of family objects: the components use the identity, log, logit and log links, other links are refused, and the default inverse link of `stats::Gamma()` is replaced by the log link with a warning. Family functions (e.g. `family = Gamma`) are accepted.
* Binomial responses may be logical or two-level factors (as in `glm()`); two-column (successes, failures) responses are refused with an explicit message. Missing and infinite values in `X`, `y` and `Z` are refused (e.g. `log(0)` in a formula), and `Z` must start with an intercept column.
* `survregMixBayes()` accepts only right-censored responses: left-, interval- and counting-process `Surv` objects, matrices with more than two columns and event codes other than 0/1 are refused instead of being silently misread.
* A leading column of ones is recognised as the intercept (it receives the intercept prior); designs without an intercept, e.g. `y ~ 0 + x`, give every column the slope prior (supplied `intercept1` / `intercept2` priors are then reported as not used).
* Starting values (`control$init`) are validated per model: `theta` must lie in (0, 1), dispersion, shape and scale starting values must be positive, the documented Weibull `scale1` / `scale2` are now accepted, and elements that do not apply to the model are reported.
* Without an explicit `burnin.iterations`, the burn-in is half of the iterations, at most 1000 (`min(1000, floor(iterations / 2))`), so the number of stored draws grows with `iterations`: the fixed default of 1000 made runs of at most 1000 iterations fail, and runs of 1001 to 1999 iterations now use a shorter burn-in than in 0.1.2 and store more draws. This also applies when `glmMixBayes()` or `survregMixBayes()` is called without `control` and with `iterations` in `...`: their default `control` is now `list(iterations = 1e4, seed = ...)`, without the fixed burn-in that made e.g. `glmMixBayes(X, y, iterations = 800)` fail. Unsupported prior distributions are reported under the name that was written (`double_exponential` was reported as `laplace`).

### Bug Fixes (also present in 0.1.2)
* In 0.1.2 only the numbers of a prior string were used and the distribution name was ignored: whatever was written, coefficients had normal priors, `theta` a beta prior, `sigma1` / `sigma2` Cauchy priors truncated at zero, and `phi1` / `phi2`, `shape1` / `shape2` and `scale1` / `scale2` gamma priors (`exponential(rate)` was read as the two numbers `1, rate`). For example, `sigma1 = "normal(0, 5)"` gave a half-Cauchy(0, 5) prior, `sigma1 = "exponential(1)"` a Cauchy(1, 1) prior truncated at zero and `phi1 = "lognormal(1, 0.5)"` a gamma(1, 0.5) prior. The distribution written is now used (unsupported ones raise an error), so fits that specified another distribution than these now differ from 0.1.2; the default priors, and prior strings that name the distributions listed above (or `exponential(rate)` for `phi1` / `phi2`, `shape1` / `shape2` and `scale1` / `scale2`, which 0.1.2 read as gamma(1, rate), the same distribution), give the same priors as before.
* `mi_with()` keeps the bases of data-dependent terms of the outcome formula (`poly()`, `scale()`, `splines::ns()`, `splines::bs()`, ...) fixed across the posterior draws: they are computed once from all analysed records (for the outcome formula stored with the fit, taken from its model frame) instead of from the records allocated to the correct matches in each draw, which put the coefficients of every draw on a different basis (e.g. orthogonal polynomials rescaled by the number of records), so that the pooled coefficients and their between-draw variance mixed these bases. As for `predict()`, only the terms whose prediction call R records are fixed: a call nested in another, such as `I(scale(x)^2)`, is still evaluated from the records of each draw (`?mi_with` says to compute such variables in `data` beforehand). `lm()` and `glm()` refits use the terms with their `predvars`; for `coxph()`, which does not accept a terms object, these terms are evaluated once and the coefficients keep their usual names (e.g. `"poly(x, 2)1"`), except penalised `pspline()` terms, which `coxph()` must see as calls: they are refitted as written, with their penalty arguments (`df`, `theta`, `method`, ...), and with the boundary knots and number of knots of all records (coefficients `"ps(x)3"`, ...). Terms without a data-dependent basis are unaffected.
* `mi_with()` now matches the rows of `data` to the records used in the fit (by row name for fits from `plglm()` / `plsurvreg()`), so records dropped by `na.action` or `subset` no longer shift the posterior allocations onto the wrong records; a `data` argument that cannot be aligned raises an error.
* `mi_with()` refits gamma-family models with `Gamma(link = "log")`, the link of the mixture components (previously the inverse link of `stats::Gamma()`), and warns when posterior draws were skipped because the refit failed or had too few correct-match records; when no draw can be used, the error says which of the two happened and shows the first refit error. Both `mi_with()` methods stop with an informative error when fewer than two draws can be used, since the between-draw variance needs at least two (the pooled standard errors, degrees of freedom and intervals were `NA`).
* `predict()` falls back to the design matrix stored by `plglm(..., x = TRUE)` / `plsurvreg(..., x = TRUE)` when no new data are given and checks the number of columns of `newx`; `predict.survMixBayes()` refuses unused arguments such as `type` instead of ignoring them.
* Intercept-only designs keep their matrix structure in the stored posterior draws (print, summary, confint, vcov and coef failed for them in 0.1.2), and `survregMixBayes()` labels the coefficient draws with the column names of `X`.
* `confint()` reports unknown parameter or block names instead of returning an empty result or a bare subscript error.
* `predict.survMixBayes()` now includes `log(scale)` in the Weibull linear predictor (through the identified intercept when the design has an intercept column; see *Breaking Changes*): the intercept and the scale are not identified separately, so predictions without it depended on the scale prior.
* `plglm()` and `plsurvreg()` with an `adjMixBayes` adjustment silently dropped `offset()` terms of the model formula (the Bayesian engines only see the model matrix); they now stop with an error. The frequentist adjustments are not affected by this change.
* `mi_with()` without `formula` takes the outcome formula from the model frame stored in the fit, instead of re-evaluating the variable named in the call, which may have changed (or disappeared) since the fit.
* `predict()` matches the columns of named new data to the coefficients by name (a reordered model matrix was used by position) when the coefficient names are non-empty and unique and each names exactly one column of the new data, and by position otherwise (e.g. for fits with unnamed design columns, such as `X = cbind(1, x)`, saved with empty coefficient names, whose names cannot be matched), with a warning when a column of the new data bears the name of a coefficient at another position.
* Summaries print with significant digits, so that small coefficients no longer print as 0.

### Output Objects
* Fitted objects gain `match.prob`, `use_logistic`, `priors` and `diagnostics` (placed after `call`, so the positions of the 0.1.2 elements are unchanged), `estimates$theta` for GLM fits and `estimates$gamma` for fits with linkage covariates (see *Breaking Changes* for `estimates$m.coefficients` and `coefficients2`). `m_samples` is stored as an integer matrix whose columns are named after the analysed records, whose names are also stored in `obs_names`. `summary()` objects gain `use_logistic`, `n_safe`, `match.prob`, `match.rate`, the `m.coefficients` table and the `theta` / `gamma` tables.
* `glmMixBayes()` and `survregMixBayes()` name the unnamed columns of `X` once (e.g. of `cbind(1, x)` or of a matrix without column names): an unnamed column of ones becomes `"(Intercept)"` and any other unnamed column `"X<j>"`, `j` being its position (unnamed columns of `Z`: `"(Intercept)"` and `"Z<j>"`); given names are kept. The coefficient draws, `summary()`, `confint()`, `posterior_draws()`, `diagnostics$ess` and the warnings therefore show these names instead of empty names (e.g. `coefficients[]`) or positions. The identified Weibull intercept is found by its values (a column of ones), whatever its name.

# **postlink 0.1.1**

### New Features
* Updated the `priors` argument for the Bayesian Mixture functions (`adjMixBayes()`, `glmMixBayes()`, `survregMixBayes()`) so that intercept priors and slope coefficient priors are now decoupled.

### Architecture & S3 Methods
* Refactored S3 class assignment system to remove false inheritance from base `glm`, `lm`, and `coxph` classes. Fitted objects now use dedicated package-level classes (e.g., `plmodel`, `plglm`, `plcoxph`).
* Added standard generic extractors (i.e., `coef()`, `vcov()`, `confint()`, `df.residual()`) for compatibility with tools like `lmtest::coeftest()`.
* Added custom methods to indicate unsupported standard likelihood and residual-based generics (e.g., `logLik()`, `profile()`, `anova()`, `extractAIC()`, `cooks.distance()`, `rstudent()`). 
* Consolidated shared printing behaviors for adjustment objects (`adjELE`, `adjMixture`, `adjMixBayes`) using a unified base `print.adjustment()` method via `NextMethod()`, reducing code duplication.
* Added an error message to clarify that the `gaussian` family in `glmMixture` is intended to be used only with the `identity` link for now.

### Documentation & Testing
* Standardized all Roxygen manual page titles to Title Case. Implemented a GitHub Actions workflow (`format-titles.yml`) for documentation styling in continuous integration.
* Removed `VignetteBuilder: knitr` from the `DESCRIPTION` file to resolve a CRAN NOTE, as the extended package articles are hosted only via `pkgdown` for now.
* Updated the `testthat` suite to align with the newly refactored S3 class structures and console outputs.

# **postlink 0.1.0**

* Initial CRAN release.
* Implements a suite of statistical tools (weighting or mixture modeling) for secondary analysis of linked data accounting for mismatch errors.
